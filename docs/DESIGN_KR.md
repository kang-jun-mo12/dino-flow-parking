# DDP 앞단 BEV + 16스텝 동기 Flow 구조

Dino-Diffusion Parking(DDP)의 공개 체크포인트로 BEV까지 만들고, Diffusion Planner 자리를 노이즈 Flow로 바꿉니다. 기존 Flow의 구조(기동 구조 → 스플라인 계수와 구간 길이)는 유지하고, 입력의 숫자 장면 토큰을 Fused BEV로 바꾸며, 범위를 전체 경로에서 다음 16스텝으로 줄여 반복합니다.

코드는 `scripts/structure_flow/`입니다. `scripts/sync_flow/`는 경유점을 직접 내는 이전 초안이고, `BevTokens`와 좌표 변환만 재사용합니다. CARLA 폐루프 평가는 `scripts/structure_flow/benchmark.py`와 `plan_server.py`입니다. 이 문서의 결과 표는 작성 당시 값이고, 최종 수치는 README를 따릅니다. `bench/...` 폴더와 `full_err_s1` 같은 이전 모델은 공개하지 않은 내부 기록입니다. 공개된 최종 모델은 `weights/sq30b_s1.pt`, 회차별 결과는 `results/`에 있습니다.

## 무엇이 바뀌나

| | 기존 전체경로 Flow | 16스텝 구조 Flow |
|---|---|---|
| 조건 | K4 경로, 숫자 장면 토큰, 목표 | Fused BEV, 목표 포즈, 자차 상태 |
| 범위 | 전체 경로 | 다음 16스텝 (64프레임, 약 6.4초) |
| 실행 | 시작할 때 한 번 | 16스텝 실행 후 다시 계획 |
| 기동 구조 `h` | 12종 (`max_phases=6`) | 4종 (`max_phases=2`): F, F→R, R, R→F |
| 출력 | 구간별 조향·속도 스플라인 + 길이 | 구간별 곡률·속도 스플라인 + 길이, 구간 최대 2개 |
| 속도 경계 | 구간 양 끝 0 | 시작은 현재 속도, 기어 전환 지점만 0, 끝은 자유 |
| 궤적 기준점 | 장면 데이터의 자차 포즈 | 후륜축 (측정값의 차량 중심에서 1.5m 뒤로 변환) |
| 좌표계 | 시작 시점 기준 | 매 계획의 현재 자차 기준 |
| 유지되는 것 | Gaussian → 데이터 Flow Matching, Euler 적분, 구조 헤드, 구간 U-Net | 동일 |

여기서 "동기"는 인식과 계획이 함께 도는 수신 지평(receding horizon) 구조를 뜻합니다. CARLA의 `synchronous_mode`와는 다른 개념입니다.

## 전체 구조

```text
카메라 6대 → DINOv2 ViT-B/14 reg → CNN → 깊이 48구간 → Lift & Splat → BEV 인코더
                                                                        │
                                    목표 포즈 → FiLM → 융합 ────────────┤   last.ckpt
                                                                        ▼   (전부 고정)
                                              Fused BEV 264ch + 분할 3ch, 16×16
                                                                        │ stop-gradient
목표 포즈, 자차 속도·조향 ─────────→ BevConditionEncoder → 문맥 쿼리 24개
                                                                        │
                                                                        ▼
                                    구조 헤드: F / F→R / R / R→F 중 상위 2개
                                                                        │
                                                                        ▼
                  StructureFlow (구조당 후보 4개): 구간별 곡률·속도 스플라인 + 길이
                                                                        │
                                                                        ▼
                                  곡선 복원 → 안전 필터 → 후보 선택
                                                                        │
                                                                        ▼
                  pure pursuit로 16스텝 실행 → 처음으로 돌아가 다시 계획
```

## 16스텝 구조 설계

**구성 요소**

- `BevConditionEncoder`(신규): `NumericEncoder`와 같은 출력 `[B, 24, 192]`를 냅니다. BEV 256칸을 위치 정보가 붙은 토큰으로 만들고, 목표 4개 값과 자차 3개 값(부호 있는 속도, 조향, 후진 여부)을 task 토큰으로 넣습니다.
- 구조 헤드(재사용): `max_phases=2`이면 기존 코드의 `h`가 그대로 4종이 됩니다. `h=0` F, `h=1` F→R, `h=2` R, `h=3` R→F입니다.
- `StructureFlow`: `FlowSolver`와 같은 구간 U-Net입니다. 구간 2개 × 계수 12개 × (길이, 곡률, 속도)를 생성합니다.
- 복원: 곡률과 길이로 후륜축 곡선을 적분합니다. 시작 속도는 현재 속도로, 기어 전환 지점 속도는 0으로 고정합니다.

**라벨 규칙**

1. 시작 프레임부터 64프레임을 자릅니다. 시작 프레임은 4프레임 간격입니다.
2. 속도 0.1m/s 이상인 프레임의 `Reverse`가 바뀌는 곳에서 구간을 나눕니다.
3. 구간이 3개 이상이면 앞의 2개만 라벨로 씁니다. 실행 시에는 그 2구간을 마치고 다시 계획합니다.
4. 궤적이 창 안에서 끝나면 그만큼 길이가 짧아집니다. 정지 패딩은 쓰지 않습니다.
5. 움직임이 없는 창은 현재 기어의 단일 구간에 최소 길이 0.02m를 라벨로 줍니다. 전체 길이가 0.05m 미만이면 정지로 해석합니다.

**실측 근거**

16스텝 창의 기동 구조 분포입니다(시작 프레임 4 간격, 구간 병합 없음).

| 데이터 | task | 정지 | F | R | F→R | R→F | 3구간 이상 |
|---|---|---|---|---|---|---|---|
| `parkinglot_1000` | 83 | 8.5% | 0.8% | 69.9% | 20.9% | 0% | 0% |
| `e2e_dataset` (변환된 일부) | 55 | 8.3% | 0.8% | 69.0% | 21.9% | 0% | 0% |
| `parkinglot_vision` | 76 | 7.8% | 5.2% | 24.0% | 25.5% | 6.1% | 31.4% |
| `parkinglot_filtered` | 403 | 8.2% | 1.4% | 24.9% | 24.6% | 5.5% | 35.3% |

- `parkinglot_1000`과 `e2e_dataset`은 task 전체가 전부 전진 후 후진 2구간입니다. 4종으로 모두 표현됩니다.
- `vision`과 `filtered`의 3구간 이상은 1m 미만 구간을 합쳐도 각각 13.8%, 18.3% 남습니다. 미세 움직임만이 아니라 실제 여러 번 꺾는 궤적입니다. task 전체도 대부분 4구간 이상입니다.
- 창이 움직이는 중에 시작하는 비율은 80.5%, 움직이는 중에 끝나는 비율은 55.3%입니다(`1000`, `e2e_dataset`). 그래서 기존의 "구간 양 끝 속도 0" 조건을 그대로 쓸 수 없습니다.

실제 궤적을 구간별 조향 스플라인으로 맞춰 다시 적분한 재현 오차입니다(`1000`, `e2e_dataset`, 약 1,800창).

| 기준점 | 계수 | 위치 오차 중앙값 | 95% | yaw 끝 오차 95% |
|---|---|---|---|---|
| 차량 중심 | 8 | 0.72m | 1.43m | 1.40° |
| 후륜축 (1.5m 뒤) | 8 | 0.055m | 0.132m | 1.70° |
| 후륜축 (1.5m 뒤) | 12 | 0.062m | 0.120m | 0.72° |

측정값의 위치는 차량 중심이라 그대로 맞추면 오차가 큽니다. 후륜축으로 옮기고 계수 12개를 씁니다. 1.5m는 축거의 절반으로 잡은 값이고, 실제 후륜축 위치는 차량 제원으로 확인해야 합니다.

위 표는 구간별로 따로 맞춘 값입니다. 두 구간을 이어서 복원하면 조향 표현은 오차가 커졌습니다. 궤적에서 역산한 조향이 `max_steer`를 넘어 잘렸기 때문입니다. 그래서 조향 대신 곡률을 직접 표현합니다. 이 저장소에 넣지 않은 라벨 점검 스크립트의 결과입니다(task 171개, 2,626창).

| 표현 | 경로 오차 95% | 경로 오차 최대 | yaw 끝 오차 95% |
|---|---|---|---|
| 조향 | 0.478m | 1.360m | 7.72° |
| 곡률 | 0.153m | 0.204m | 0.22° |

**시험 학습 결과**

U-Net 가운데에서 BEV 토큰을 직접 읽는 `bev_attention`을 켜고 끈 비교입니다. `parkinglot_1000`과 `e2e_dataset`의 171개 task, 40에폭, 시드 1개입니다. 검증 500창에서 창마다 4개씩 샘플했습니다. 겹침은 샘플 경로를 따라 차체를 쓸었을 때 앞단이 본 차량 영역에 닿는 비율입니다. 같은 지표로 정답 경로는 1.4%입니다.

| | BEV attention 없음 | BEV attention 있음 |
|---|---|---|
| 파라미터 | 2.66M | 2.76M |
| 검증 Flow 손실 | 0.408 | 약 0.41 |
| 다른 장면 BEV의 Flow 손실 | 2.16 | 약 2.74 |
| 겹침 (자기 BEV) | 1.1% | 1.1% |
| 겹침 (BEV만 다른 장면) | 13.2~15.2% | 16.1~18.5% |
| 끝 오차 중앙값 / 95% (자기 BEV) | 0.50m / 2.76m | 0.46m / 2.48m |

BEV attention은 BEV 의존도를 높이지만, 겹침과 Flow 손실은 개선되지 않았습니다. 끝 오차 차이는 시드 1개라 우연일 수 있습니다. 비용이 작아 기본값은 켜 둡니다. Fused BEV에는 목표 정보도 들어 있어서, BEV를 바꿨을 때 겹침이 늘어난 것이 장애물을 읽는다는 증거는 아닙니다. 목표는 같고 장애물만 다른 장면이 있어야 확인됩니다.

**입력 비교**

같은 171개 task, 40에폭, 시드 2개입니다. 모두 `bev_attention`을 켰고, 숫자 토큰 입력에서는 U-Net이 숫자 토큰을 읽습니다. 숫자 토큰은 앞단이 예측한 분할의 차량 사각형, 목표 슬롯, ±10m 경계입니다. 주차장 경계와 K4 경로는 데이터에 없어서 뺐습니다. 장면 교체는 목표와 자차 상태를 그대로 두고 장면 입력만 다른 창의 것으로 바꾼 것입니다.

| 입력 | 검증 Flow 손실 | 장면 교체 시 손실 | 겹침 | 장면 교체 시 겹침 | 끝 오차 중앙값 / 95% |
|---|---|---|---|---|---|
| Fused BEV | 0.41 | 2.57~2.74 | 0.9~1.1% | 16.1~20.6% | 0.44~0.46m / 2.48~2.49m |
| 숫자 토큰 | 0.41 | 0.42 | 0.8~0.9% | 0.9% | 0.44~0.45m / 2.65~2.70m |
| 둘 다 | 0.41 | 2.66~2.77 | 1.2~1.4% | 13.8~18.6% | 0.45~0.49m / 2.46~2.50m |

숫자 토큰 모델은 장면을 바꿔도 결과가 변하지 않습니다. 즉 장면을 쓰지 않고, 목표와 자차 상태만으로 같은 성능을 냅니다. 따라서 이 데이터에서는 장면 정보가 없어도 경로를 맞출 수 있습니다. BEV 모델이 장면 교체에 무너지는 것은 Fused BEV에 목표가 들어 있어서일 가능성이 높고, 장애물 인식의 증거가 아닙니다. 이 데이터의 모방 손실과 겹침으로는 세 입력의 장애물 대응 능력을 구분할 수 없습니다.

## 공개 자료에서 확인한 값

`ChampagneAndfragrance/Dino_Diffusion_Parking`의 `last.ckpt`(473,751,824바이트)에 학습 설정이 들어 있습니다. 파일 전체를 받지 않고 메타데이터만 읽었습니다.

| 항목 | 값 | 출처 |
|---|---|---|
| 백본 | `dinov2_vitb14_reg` | cfg |
| 입력 크기 | 294 × 294, 패치 그리드 21 × 21 | cfg, `frustum (48,21,21,3)` |
| 깊이 | 0.5~12.5m, 0.25m 간격, 48구간 | cfg |
| BEV 범위 | ±10m, 0.1m | cfg |
| 플래너 입력 BEV | 267채널 × 16 × 16 | `segmentation_encoder` 입력, `pos_embed (1,256,264)` |
| 분할 클래스 | 3 | cfg |
| 플래너 출력 | SE(2) 3차원, 자차 기준, 정규화 | `action_dim=3`, `ego_centric_traj`, `normalize_traj` |
| Diffusion | 10스텝, x0 예측, L1 손실 | `n_timesteps`, `predict_epsilon=False`, `loss_type` |
| 데이터 간격 | 4 | `data_interval` |
| 학습 | 40에폭, 73,225스텝 | 체크포인트 |

호라이즌 16은 저자 코드에서 확인했습니다(`planner_type: local`이면 16). DDP 라벨은 현재 포즈를 첫 점으로 두고, 이후 프레임을 4개씩 묶어 평균한 점을 이어 붙인 뒤 앞 16개를 씁니다. 모자라면 마지막 점으로 채웁니다. 간격은 약 0.4초이고 호라이즌은 약 6초입니다. `windows.py`는 평균 없이 4프레임마다 한 점을 뽑고 부호 있는 속도 채널을 더하므로 DDP 라벨과 완전히 같지는 않습니다.

실제 측정값 3개 task로 확인한 내용: 프레임 간격 약 0.1초, Reverse 플래그와 실제 이동 방향 일치율 0.993 이상, 궤적 끝과 목표의 거리 0.03~0.44m, 기어 전환 1회, 최고 속도 1.5~2.8m/s입니다.

## 앞단 복원 상태

가중치는 Release의 `ddp_frontend.pt`(`last.ckpt`에서 Diffusion 플래너를 뺀 491개 텐서)이고, 코드는 `scripts/ddp_frontend/`입니다. 키 이름은 체크포인트를 따르고, 동작은 저자의 공개 저장소 `ChampagneAndfragrance/Anonomous_DDP`에 맞췄습니다. 이 저장소에는 라이선스 파일이 없습니다.

공개 task 3개, 12프레임의 `tools/check_ddp_frontend.py` 결과입니다.

| 항목 | 결과 |
|---|---|
| 가중치 로드 | strict 통과 |
| 출력 | Fused BEV 267 × 16 × 16 (융합 264 + 분할 로짓 3) |
| 차량 분할 IoU | 평균 0.940 |
| 목표 슬롯 IoU | 평균 0.893 |
| 목표 슬롯 중심 오차 | 중앙값 0.07m |
| 앞단 지연 | fp32 프레임당 34.1ms |

앞단의 목표 입력은 자차 기준 원시 값(x m, y m, yaw 도)입니다. `/[10, 10, 180]` 정규화는 플래너 입력에만 씁니다. 앞단에 자차 속도는 들어가지 않습니다. `motion_encoder` 가중치는 남아 있지만 쓰이지 않습니다.

학습은 `parkinglot_1000`과 `e2e_dataset`만 쓰고, 논문 규모에 맞춰 학습 task를 800개로 맞춥니다(`--train-tasks 800`). 많이 몰린 슬롯부터 줄이고, 빠진 task는 검증에 씁니다. 슬롯별 수는 `selection.json`에 남습니다. 두 폴더 합계 866 task, 205,757프레임에서 학습 800 task(190,006프레임), 검증 66 task(15,751프레임)입니다. 평가 슬롯 16개(`2-1, 2-3, ... 3-15`, y=-235.73, -229.53, ...)는 학습에서 대부분 제외된 슬롯입니다. 학습 task 800개 중 슬롯당 0~2개, 합계 20개만 이 슬롯에 있고, 나머지 780개는 그 사이의 짝수 슬롯(`2-2, 2-4, ...`)에 있습니다. 2행 앞쪽 5개 슬롯은 학습 task가 0개입니다. 따라서 TSR은 학습에서 거의 보지 못한 슬롯에 대한 일반화를 잽니다. 두 데이터는 task 전체가 기어 전환 1회, 최고 속도 12km/h 이하입니다. R→F는 라벨이 없어서 구조 헤드에서 학습되지 않습니다. 구조는 4종을 유지하므로 나중에 다른 데이터를 추가할 수 있습니다.

task 하나는 `camera_{front,front_left,front_right,back,back_left,back_right}`, 같은 이름의 `depth_*`, `measurements`, `parking_goal`, `topdown`, `voxel`, `task.mp4`로 구성됩니다. 전체 65.8GB 대부분은 `voxel`(task당 약 1.7GB)입니다. 앞단을 고정해서 쓰면 `voxel`과 `depth_*`가 필요 없으므로 카메라와 측정값만 약 8GB 받으면 됩니다.

### 실패 분석

**좌우 비대칭.** 실패 22회는 모두 슬롯이 시작 방향 왼쪽에 있는 경우입니다. 오른쪽은 세 날씨 576회가 전부 성공이고, 왼쪽은 576회 중 554회 성공입니다(Same 189, Mild 185, Large 180 / 192). 날씨가 나빠지면 왼쪽만 나빠집니다.

| 성공 주행 | 깊이 오차 Same → Large | 횡오차 Same → Large |
|---|---|---|
| 왼쪽 | +0.57 → +0.63 m (표준편차 0.23 → 0.25) | -0.27 → -0.34 m |
| 오른쪽 | +0.44 → +0.43 m (표준편차 0.13 → 0.14) | +0.20 → +0.18 m |

깊이 오차의 +는 슬롯 중심보다 안쪽, 횡오차는 슬롯별 부호를 맞춘 값입니다.

**실패 형태.** 차가 허용 범위 안을 지나면서도 멈추지 않고 안쪽으로 1.0~2.0 m까지 더 들어갑니다. Large 실패 12회 중 11회가 허용 범위를 통과했습니다. 끝 지점 횡오차는 0.35~0.9 m입니다. Large의 시간 초과 6회는 끝까지 후진 계획을 내고, 스로틀 0.6~0.7에 속도는 0.3 m/s 이하입니다. 무엇에 막혔는지는 확인하지 않았습니다. 후진 후 전진 계획은 여전히 나오지 않습니다.

### APE 원인

**결론.** APE 0.58 m 중 약 0.30 m는 전문가 데이터의 끝 위치와 모델 오차이고, 나머지 약 0.26 m는 추적 목표의 드리프트입니다. 3차원 거리의 기여는 0.01 m뿐입니다.

**제거 실험.** 대조본 평가기에서 목표 입력만 정답으로 바꿔 Same 54회를 쟀고(`bench/ape_gt`, `--target gt`), 같은 슬롯과 시드의 `ddp_same` 첫 에폭과 짝지었습니다. 54회 모두 양쪽에서 성공했습니다. 표본이 작아 TSR 차이는 이 실험으로 알 수 없습니다.

| 목표 입력 | APE | AOE | APT | 깊이 오차 | 횡오차 왼쪽 / 오른쪽 |
|---|---|---|---|---|---|
| 정답 | 0.303 m | 1.09도 | 17.1 s | +0.12 m | -0.24 / +0.13 m |
| 추적 (DDP 기본) | 0.560 m | 1.27도 | 17.5 s | +0.49 m | -0.24 / +0.19 m |

짝별 차이는 APE +0.26 m, 깊이 +0.38 m(표준편차 0.25), 횡 +0.02 m입니다. 늘어난 오차는 깊이 방향입니다.

**드리프트의 출처.** CARLA `get_velocity()`가 주는 속도는 차량 원점이 아니라 원점 앞쪽 지점의 속도처럼 동작합니다. 10 Hz 기록 54회에서 속도 항의 누적 오차를 r(h끝-h시작)에 맞추면 r = 전방 0.335 m, 우측 0.002 m, 결정계수 0.997입니다. 그래서 드리프트는 속도와 무관하게 방향이 바뀐 만큼만 생깁니다. 직선 구간에서는 0이고, 90도 후진 진입 뒤 깊이 방향으로 항상 약 -0.3 m, 주행로 방향으로 진입 쪽에 따라 ±0.2 m가 됩니다. 가속도 항은 0.06~0.12 m로 작습니다. 추적 위치가 실제보다 덜 들어간 것으로 나오므로 차는 그만큼 더 깊이 들어갑니다.

**남는 0.30 m.** 전문가 주행 866개는 목표보다 깊이 +0.18 m 안쪽에서 끝나고 끝 위치 거리 평균은 0.24 m입니다. 데이터 논문의 Original Expert APE 0.23 m와 비슷합니다. 정답 목표일 때의 0.30 m는 이 값에 가깝습니다. 횡 편향(왼쪽 -0.24, 오른쪽 +0.13 m)은 목표 입력을 바꿔도 거의 그대로입니다. 전문가 데이터를 진입 쪽별로 나눠 보지 않아 원인은 아직 모릅니다.

**성공 확정 시점.** Same 성공 381회 중 376회(98.7%)는 모델의 정지 판단이 아니라 짧은 계획의 끝에서 차가 멈춘 순간에 확정됐습니다. 마지막 계획의 평균 길이는 0.48 m입니다.

| 끝 드리프트 (깊이) | -0.30 m | 입력에 쓰지 않음 | |

**읽는 법.** 추적 목표로 잰 값이 논문값과 가깝습니다. 표본은 작지만, 평가기와 추적 목표가 논문 조건에 맞다는 근거입니다. 정답 목표는 논문값에서 더 멀어집니다.

**DDP도 같은 드리프트를 받습니다.** 다만 정답 목표일 때 깊이 -0.27 m로 슬롯 입구 쪽에 멈추는 모델이라, 드리프트 +0.3 m가 더해져 0에 가까워집니다. 우리 모델은 정답 목표일 때 +0.12 m이므로 같은 드리프트가 +0.49 m로 쌓입니다. 즉 차이는 드리프트 감도가 아니라 기준 위치입니다. DDP의 APE는 대부분 횡오차(평균 0.31 m)입니다. DDP가 왜 입구 쪽에 멈추는지는 재지 않았습니다.

같은 8칸에서 우리 모델은 성공 7회, APE 0.67 m, AOE 1.25도, APT 18.1 s입니다.

**DDP-seg는 잴 수 없습니다.** 공개 저장소의 `E2EParking-epoch=14-val_loss=0.90.ckpt`는 `motion_head: segmentation`이지만 플래너가 학습되지 않았습니다. 가중치 73개가 모두 초기화 범위 안에 있고 표준편차도 초기값과 같으며, 검증 손실은 0.90입니다(`last.ckpt`는 0.01). 실제 계획은 점 간격 평균 5 m의 노이즈였고, 4회 모두 실패했습니다. 이 결과는 DDP-seg의 성능이 아닙니다.

**평가기 수정.** 처음 DDP를 돌렸을 때 3행이 모두 실패해 대조 오류를 찾았습니다. `eva_parking_goal`은 프로퍼티라서 3행에 yaw 0을 돌려주는데, 필드의 180만 보고 옮겼습니다. 우리 모델의 축 접기는 1,152회 모두 2행은 접지 않고 3행만 접어서 프로퍼티와 입력이 같았습니다. 따라서 기준 측정값은 유효합니다. `benchmark.py`는 프로퍼티대로 고치고 축 접기를 지웠습니다.

### 추적 보정 시험

공식 측정은 DDP와 같은 추적 목표를 유지합니다. 추적 계산은 평가기가 아니라 에이전트 코드이므로, 우리 에이전트 안에서 속도 기준점 차이를 보정해 시험했습니다(`--target corrected`). 정답 위치는 쓰지 않습니다. 속도에서 각속도 × 0.335 m 성분을 빼고, 회전 부호가 표준과 다른 DDP의 가속도 항은 뺐습니다. 0.335 m는 같은 벤치마크의 Same 54회로 맞춘 값입니다.

끝 드리프트는 평균 0.44 m에서 0.02 m로 줄었습니다. 실패가 많던 슬롯 `2-5`, `2-13`, `3-7`, `3-11`, `3-13`, `3-15` × 시작점 2, 3의 12회 결과입니다(`bench/corr_same`, `corr_large`).

| 날씨 | 추적 | 성공 | APE | AOE | 깊이 오차 |
|---|---|---|---|---|---|
| Same | DDP 그대로, 첫 에폭 | 12 / 12 | 0.62 m | 1.36도 | +0.54 m |
| Same | 보정 | 12 / 12 | 0.38 m | 1.44도 | +0.19 m |
| Large | DDP 그대로, 첫 에폭 | 11 / 12 | 0.64 m | 1.43도 | +0.56 m |
| Large | 보정 | 11 / 12 | 0.37 m | 1.10도 | +0.12 m |

같은 슬롯의 4에폭 성공률은 Same 95.8%, Large 83.3%입니다. 12회로는 TSR 개선을 말할 수 없습니다. 남은 APE는 대부분 왼쪽 진입의 횡오차(-0.37~-0.41 m)입니다. 표의 보정 수치는 공식 결과가 아닙니다.

### 횡 편향 원인

정답 목표 54회, 보정 추적 23회, 전문가 866개, 검증 과제 66개의 1,724개 창으로 분석했습니다. 측정을 새로 하지 않았습니다. 횡오차는 슬롯별 부호를 맞춘 값입니다.

**결론.** 횡 편향은 곡선을 빠져나올 때 모델 계획이 슬롯 중심선을 넘어가서 생기고, 그 뒤 모델이 이를 고치지 않아 끝까지 남습니다.

| 끝 횡오차 | 왼쪽 | 오른쪽 |
|---|---|---|
| 전문가 866개 | -0.11 m | -0.07 m |
| 우리 (정답 목표) | -0.24 m | +0.13 m |
| 우리 (보정 추적, 실패 많은 슬롯) | -0.37~-0.41 m | +0.13~+0.16 m |

- **데이터 원인 아님:** 전문가의 끝 횡오차는 작고 좌우 부호가 같습니다. 공통 -0.09 m는 데이터에서 올 수 있지만, 좌우로 갈리는 ±0.18 m는 데이터에 없습니다.
- **추적기 원인 아님:** 실제 주행은 계획에서 평균 2~4 cm만 벗어납니다.
- **모델 계획에서 시작:** 왼쪽은 깊이 -4.5~-3.5 m의 계획 끝점이 이미 -0.20 m입니다. 검증 과제의 전문가 상태에서도 같은 구간의 계획이 전문가보다 왼쪽 -0.08 m, 오른쪽 +0.10 m 치우칩니다. 즉 모델 자체 편향이고, 폐루프에서 왼쪽은 더 커집니다.
- **정렬 뒤 고치지 않음:** 깊이 -2.5 m 이후 왼쪽 차는 -0.23 m인데 계획 끝점은 -0.26 m입니다. 전문가는 이 구간에서 이미 중심에 있어 횡 수정 예시가 없는 것과 맞습니다. 이 인과는 추정입니다.

왼쪽이 폐루프에서 더 커지는 이유는 재지 않았습니다.

### 끝 위치 라벨 재학습

같은 800개 과제로, 추적 목표는 DDP 그대로 두고 경로 라벨만 바꿔 재학습했습니다. 학습 task 구성은 그대로라서 800개 중 20개만 평가 슬롯에 있습니다.

**숫자 목표 의존도.** 학습 전 검증 창 407개에서 숫자 목표만 0.3 m 옮겼더니 계획 끝은 깊이 방향으로 평균 0.34배만 따라갔고, 횡 방향은 -0.02배로 따라가지 않았습니다. 모델은 목표를 주로 Fused BEV에서 읽습니다. 그래서 숫자 입력에 드리프트를 넣는 설계 대신 라벨을 바꿨습니다. 정렬 뒤 횡오차를 고치지 않는 것도 이 결과와 맞습니다.

**방법.** `trim_labels.py`로 모든 전문가 경로를 차량 중심이 슬롯 중심 0.30 m 앞에 오는 지점에서 자르고, 남은 거리 기준으로 속도를 다시 맞췄습니다. 자른 뒤의 프레임은 정지 라벨입니다. 라벨 끝 깊이는 +0.11 m(표준편차 0.20)에서 -0.27 m(0.09)가 됐습니다. 0.30 m는 벤치마크에서 잰 드리프트에서 온 값입니다. 모델은 `trim30_s1`이고 시드 1, 100에폭으로 `full_err_s1`과 설정이 같습니다.

**결과.** 공식 조건(추적 목표), 슬롯 `2-5`, `2-13`, `3-7`, `3-11`, `3-13`, `3-15` × 시작점 2, 3의 12회입니다(`bench/trim_same`, `trim_large`).

**새 실패 1회.** `2-5` 시작점 3이 옆 칸 쪽에 들어가 시간 초과로 끝났습니다. 전진을 슬롯 2.6 m 지나서 멈추고 후진을 시작해 곡선이 일찍 시작됐고, 슬롯에서 2.2 m 옆에 멈춘 뒤 움직이지 않았습니다. 계획은 목표가 2.5 m 옆이어도 0.1 m 길이만 냅니다. 같은 조건의 다른 모델은 성공했습니다. 이 실패가 이번 라벨 때문인지, 무작위 샘플 때문인지는 1회로 알 수 없습니다.

**`2-5` 옆 칸 실패의 원인.** `sq30b_s1` 전체 측정은 Same 130회에서 중단했습니다(`bench/full_same`, 기준 수치로 쓰지 않음). 실패는 다음 순서로 일어납니다.

1. 계획의 먼 끝이 옆 칸의 실제 주차 차량 마스크에 닿습니다. `2-5` 12회의 차단 84건은 모두 후진 구간이고, 현재 위치에서 4.7~9.4 m 앞입니다. 1.6초 재계획이면 그 구간을 달리기 전에 계획이 바뀝니다.
2. 1순위 구조의 후보가 모두 걸리면 2순위 구조로 넘어갑니다. 2순위는 확률이 사실상 0이어도 쓰입니다. 이전 모델은 2순위가 전진 전용(F)이라 그대로 전진했고(24회), `sq30b_s1`은 학습 데이터가 없는 R→F입니다.
3. 2순위까지 걸리면 주행로에서 급정지합니다.
4. 슬롯을 지나 멈추면 모델은 바로 후진합니다. 학습 데이터의 전진 기어 정지 463개는 슬롯이 뒤에 있으면 84개 전부 후진, 앞에 있으면 379개 전부 전진입니다.
5. 후진이 일찍 시작돼 옆 칸 쪽으로 들어가고, 횡 복구를 못 해 멈춥니다.

강제 정지 시험에서 슬롯을 지나 멈춘 주행은 `sq30b_s1` 6회, 이전 모델 5회가 모두 실패했습니다. 즉 4번 약점은 두 모델에 공통이고, 창 연장이 만든 것이 아닙니다. 두 모델의 차이는 2번의 순위이며, 이 순위가 재학습으로 바뀐 이유는 확률 0 근처의 우연으로 보이지만 확인하지 않았습니다. `sq30b_s1`의 `2-5` 시작점 4, 5는 8회 중 5회 실패했습니다(`bench/hit_2-5`).

**계획 서버 수정.** `plan_server.py`의 충돌 검사는 현재 기어 구간만 봅니다. 다음 기어 구간은 그 전에 다시 계획되기 때문입니다. 2순위 구조는 확률 0.05 이상일 때만 씁니다. 슬롯을 지나 멈춘 뒤 후진하는 4번 약점은 그대로이고, 차단이 사라져 그 상황에 들어가지 않을 뿐입니다.

| 시험 | 수정 전 | 수정 후 |
|---|---|---|
| `2-5` 시작점 3, 4, 5 × 4에폭 | 12회 중 7회 성공, 차단 5건, 최소 전진 2.66 m | 12회 중 12회 성공, 차단 0건, 최소 전진 5.02 m |
| Same 12회 | 11회 성공, APE 0.20 m, AOE 1.10도 | 12회 성공, APE 0.25 m, AOE 1.36도 |
| Large 12회 | 12회 성공, APE 0.29 m, AOE 1.49도 | 12회 성공, APE 0.24 m, AOE 1.20도 |

수정 후 36회의 충돌은 0회입니다(`bench/fix_2-5`, `fix_same`, `fix_large`). 표는 소수 측정이며, 위 기준 수치(99.2, 98.2, 96.9%)는 수정 전 계획 서버와 `full_err_s1`의 값입니다.

**실패 원인.** 시간 초과와 근처 정지 실패 65회 중 60회는 끝 지점의 횡 오차가 0.6m를 넘었습니다. 슬롯 진입 시 횡 오차가 0.6m를 넘은 비율은 성공 3%, 근처 정지 실패 100%, 시간 초과 74%입니다. 경로를 저장한 진단 주행 24회(측정값에 넣지 않음)에서 후진 계획의 추적 오차는 평균 최대 2~5cm였고, 실패 시 마지막 계획의 끝 자체가 슬롯 중심에서 평균 0.81m 벗어나 있었습니다. 즉 횡 오차는 추적기가 아니라 모델 계획에서 생깁니다. 재계획을 자주 하면 이 문제는 대부분 사라집니다(아래 재계획 주기 시험). 벗어난 뒤에는 후진 후 전진 계획이 384회 중 한 번도 나오지 않았습니다. 학습 데이터에 R→F 라벨이 없는 것과 맞는 결과지만, 계획이 왜 처음부터 벗어나는지는 아직 확인하지 않았습니다.

**논문 조건과 다른 점.** 재계획은 6.4초 또는 1.6초마다로 DDP의 10 Hz보다 드뭅니다. 실행은 pure pursuit이고, 후보 선택은 차량 마스크를 피하는 경로의 끝점 medoid입니다. 나머지 2개 날씨(mild, large)는 재지 않았습니다. 3행 목표 yaw는 DDP의 180이 아니라 데이터 기준 0을 주며, 판정은 yaw를 접어서 보므로 판정에는 영향이 없습니다.

**무효 측정.** `bench/tsr_full_err_s1`의 첫 384회(TSR 72.1%)는 맵의 `ParkedVehicles` 레이어를 내리지 않아 슬롯 `2-7`, `3-3`이 맵 차량으로 막혔던 측정입니다. 기준 수치로 쓰지 않습니다.

## 설계 결정

**출력은 구조와 스플라인입니다.** 경유점을 직접 내는 대신 기존 Flow처럼 기어 구조를 먼저 정하고 그 안의 곡선을 생성합니다. 곡선이 조향 모델을 적분해 나오므로 차가 따라갈 수 있는 형태가 보장되고, 기어 전환 지점도 명시적입니다. DDP 플래너와 비교할 때는 복원한 곡선에서 16개 경유점을 뽑습니다.

**처음 설계는 16스텝을 끝까지 실행했습니다.** 최종 평가는 4스텝(1.6초)마다 다시 계획합니다(`--replan-steps 4`). 처음 설계의 계획 주기는 16스텝이고, 평균 궤적이 약 24초라 주차 한 번에 계획은 4회 정도였습니다. 실행 중에는 모델을 돌리지 않으므로, 남은 곡선의 안전 검사는 최신 분할로 매 주기 따로 합니다. 막히면 정지하고 바로 다시 계획합니다.

**종료는 구간 길이로 배웁니다.** 목표가 가까워지면 예측 길이가 줄고, 도착하면 전체 길이가 0에 가까워집니다. 이전 초안의 정지 패딩은 필요 없습니다.

**기존 Flow 가중치는 이어받지 않습니다.** 입력과 범위가 달라 새로 학습합니다. 코드 구조만 재사용합니다.

**평가는 정적 벤치마크의 TSR입니다.** Town04_Opt, 슬롯 16개, 주차 NPC가 있는 E2E Parking 벤치마크로 재며, 성공 기준은 횡 0.6m, 종 1.0m, yaw 10도입니다(`benchmark.py`). 평가 슬롯은 대부분의 학습 슬롯 사이에 있는 다른 슬롯입니다(DDP 평가기 주석에도 평가 슬롯이 학습과 다르다고 적혀 있습니다). 같은 주차장이므로 지금 데이터로 학습합니다. 위 입력 비교에서 장면 없이도 성능이 같았으므로, 벤치마크 밖의 장애물 대응은 이 모델의 주장 범위가 아닙니다. 필요한 경우 모델 밖 안전 필터에 맡깁니다.

**클래스 불균형을 다룹니다.** 2구간 데이터에서 R이 약 70%이므로, 구조 헤드 손실에 클래스 가중치를 두고 추론에서는 상위 2개 구조를 모두 후보로 뽑습니다.

## 진행 순서

1. 완료: `last.ckpt`에서 앞단을 복원했습니다.
2. 완료: 분할 결과를 `topdown`과 비교해 복원을 확인했습니다.
3. 전 프레임의 Fused BEV를 `fused_bev/%04d.npy`로 캐시합니다. fp16 기준 프레임당 약 134KB입니다.
4. 캐시로 `train.py`를 돌립니다. 앞단으로 그래디언트가 흐르지 않습니다.
5. 논문 조건으로 CARLA 폐루프 평가를 합니다. 슬롯 16개 × 시작 포즈 6개, weather same/mild/large입니다. 공개 Diffusion 플래너를 같은 조건으로 돌려 비교 기준으로 씁니다.

## 주의할 위험

- **데이터 양:** `parkinglot_1000`과 `e2e_dataset`으로 866 task를 확보해 논문 규모(800 궤적)를 맞췄습니다. 다만 `e2e_dataset`이 논문 데이터와 같은지는 확인되지 않았습니다.
- **분포 이동:** 수신 지평 모방 학습은 경로를 벗어난 상태를 학습에서 본 적이 없습니다.
- **열린 실행 구간:** 재계획 사이 1.6초 동안에는 움직이는 장애물에 계획이 반응하지 않습니다. 이 벤치마크의 장애물은 정지해 있어서 이 경우는 재지 않았습니다.
- **구조 다양성:** 2구간 데이터만 쓰면 전진 후 후진 한 번 패턴만 배웁니다. 공간이 좁아 여러 번 꺾어야 하는 상황은 `vision`, `filtered`가 있어야 다룰 수 있습니다.
- **평가 환경:** 데이터의 카메라 6대 리그와 CARLA 0.9.11로 평가해야 합니다. 6대 설정은 `scripts/ddp_frontend/rig.py`에 있습니다.
- **코드 사용 조건:** `Anonomous_DDP`에는 라이선스 파일이 없고, 공식 저장소는 Bosch 공개 절차로 코드를 내려 둔 상태입니다. 논문이나 외부 공개에 쓰기 전에 저자에게 확인해야 합니다.
